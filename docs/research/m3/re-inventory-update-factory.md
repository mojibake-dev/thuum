# RE: the InventoryUpdateData factory, or why `CreateUIMessageData` hands the fork a null (2026-10-29, 06:24Z)

The re-analyst's read of playtest 37's "not posted: the queue gave no message data" (ItemMenuRefresh.cpp, both seats, chest and body, menu open, target handle equal). pyghidra on `/SkyrimSE-1.6.1170.0.exe.unpacked.exe` (REA failed to connect this session). Every id is the AE Address Library id, resolved both ways through lab/addr.py against addrlib/versionlib-1-6-1170-0.bin; every CommonLibSSE-NG citation is to the b93280e8 pin in this tree. Engine names beyond CommonLib's, and every inferred behaviour, are HYPOTHESIS until the Frida plan at the end confirms them.

## The short answer

The fork asked the wrong function. `Offset::UIMessageQueue::CreateUIMessageData` (Offsets.h:570, AE 82169, RVA 0xfa8430) is not a factory call: it hands out a pre-made object from a per-name pool kept in the queue's own hash map (`unk348`, UIMessageQueue.h:33), and no pool exists for "InventoryUpdateData", so it returns null every time, menu or no menu. CommonLib's own header comment already warns about it (UIMessageQueue.h:25). The engine creates an InventoryUpdateData through the `MessageDataFactoryManager` (BSTCreateFactoryManager.h:30-42), whose creator for that name is registered at process start. CommonLib binds both the factory and the engine's posting function: `RE::SendUIMessage::SendInventoryUpdateMessage(owner, obj)` is AE 52849 (SendUIMessage.cpp:10, included by Skyrim.h:1389). The earlier read's "CommonLib has no binding" was wrong.

## Q1. What 82169 does and when it is null (HYPOTHESIS, high)

`FUN_140fa8430(UIMessageQueue* this, const BSFixedString& name)`: hashes the name (68221, `CRC32Calculator`, Offsets.h:199), looks it up in the BSTHashMap at this+0x348 (capacity at +0x354, sentinel +0x360, entries +0x370: BSTHashMap.h:577, 647), takes the mapped `BSTArray<IUIMessageData*>*` (data +0, size +0x10; BSTArray.h:47, 140-141) and returns the first element whose byte at +8 is zero, after setting it to 1 (the low byte of `IUIMessageData::unk08`, IUIMessageData.h:13: an in-use mark). It returns null when the name has no map entry, when the array is empty, or when every pooled object is in use. It never consults the factory manager. Its 31 callers are HUD paths (`HUDMenu_SendActivateText` 51619 and `PlayerCharacter::UpdateCrosshairs` 40621 among them, PlayerCharacter.cpp:227); the two read both pass `InterfaceStrings+0x10`, "HUDData" (InterfaceStrings.h:18). The UI constructor (82072, RVA 0xfa32f0, which also builds the `UIMessageQueue` in place at 412047) leaves the map empty; the filler that pools HUDData was not found in this read. The release side is `ProcessCommands` (82167, Offsets.h:571): for each used `messagePool` slot it deletes the data through its virtual destructor when the byte at +9 is zero, and only clears the byte at +8 when it is not (so +9 marks a pooled object; HYPOTHESIS).

## Q2. The factory, its registration, its name

`MessageDataFactoryManager::GetSingleton` (52875, Offsets.h:393, RVA 0x977710) returns the static object at 401328 (its `BSTStaticHashMap<BSFixedString, const IBSTCreator*, 16>` at 401329, 0x1a0 bytes, matching sizeof 0x1A8 at BSTCreateFactoryManager.h:42) after a thread-safe static init. The by-name creator is the free function at AE 35855 (RVA 0x61bba0; no CommonLib binding; HYPOTHESIS name `CreateUIMessageData(const BSFixedString&)`): same init guard, hash, bucket walk on pointer equality of the interned string, then `creator->vfunc[1]()`, which is `IBSTCreator::CreateImpl` (IBSTCreator.h:13). Null when the map has no entries, the name is absent, or the mapped creator is null.

Registration: the dynamic initializer at AE 7473 (RVA 0xbfb50) builds `BSFixedString("InventoryUpdateData")` (69161, BSFixedString.h:194), constructs the static `AutoRegisterCreator<InventoryUpdateData, ...>` at 406599 with vtable 216292 (Offsets_VTABLE.h:4130), inserts it into the manager's map (52862) and registers an atexit destructor. Its address sits in the CRT initializer table at 0x14175eae0 beside the other message data types' initializers, so it runs before WinMain and is present whenever any menu is open. The literal at 216293 has exactly two users: that initializer and the `InterfaceStrings` constructor (82485), which stores it at +0x58; the name the fork passes is the same interned string, no mismatch possible. The creator's `CreateImpl` is AE 52803 (RVA 0x975cb0, slot 1 of the vtable): `MemoryManager::Allocate(0x20)` (68115, MemoryManager.h:39), `unk08 = 0`, vtable `VTABLE_InventoryUpdateData` 216346 (Offsets_VTABLE.h:4149), `inventoryRef` = the global at 400312 (HYPOTHESIS: the invalid RefHandle constant), `updateObj = nullptr`. Size 0x20 matches InventoryUpdateData.h:21. The Papyrus natives `ObjectReference.AddItem` (56489, 56490) and `RemoveItem` (56098), the `MoveTo` native (56626, Offsets.h:545), `TESObjectREFR::RemoveItem` (19689) and `ItemList::Update` (51031, Offsets.h:351) all reach the data through 52849, which calls 35855; none allocates by hand.

## Q3. 52849 exactly

`void FUN_140976a80(TESObjectREFR* owner, TESBoundObject* obj)`, the signature CommonLib declares (SendUIMessage.h:10). It posts the message itself: when `UI::numItemMenus != 0` (400327 + 0x164, UI.h:130), the byte at 406594 (RVA 0x31af788) is zero and `owner` is non-null, it creates the data through 35855 with `InterfaceStrings+0x58`, sets `inventoryRef` to `CreateRefHandle(owner)` (12326, Offsets.h:580) or the 400312 constant when the ref holds no handle bits, sets `updateObj` only when non-null, and calls `UIMessageQueue::AddMessage(queue, InterfaceStrings+0xD0 "Top Menu", 8, data)` (13631, Offsets.h:569; UIMessageQueue.h:24). Outside those gates it does nothing and says nothing. The byte 406594 is written only by the take-all routine 51153 (RVA 0x8fdd60): 1 at entry, 0 before it posts kHide to "ContainerMenu". The earlier read named this gate "405989"; 405989 (RVA 0x31acf8c) is a different byte, touched only by `ContainerMenu::ProcessMessage` (51126), the worn-armour flag. `AddMessage` takes a `UIMessage` from the 64-slot pool (heap when full), copies menu, type and data, and pushes it; the data is then the queue's to delete after processing.

## Q4. The call to make

- A. `RE::SendUIMessage::SendInventoryUpdateMessage(&owner, nullptr)`. One line, zero ids of ours, the engine's shape. Risk: silent when `numItemMenus` is 0 or a take-all is running, and the fork's own header records `UI::IsItemMenuOpen()` (UI.cpp:40-43) reading false with a ContainerMenu open on the seats (ItemMenuRefresh.h:14-19). If that read was right, A posts nothing on the seats.
- B. The same creator, no gate: `auto* mgr = RE::MessageDataFactoryManager::GetSingleton(); auto* creator = mgr->GetCreator<RE::InventoryUpdateData>(strings->inventoryUpdateData); auto* data = creator ? creator->Create() : nullptr;` (BSTCreateFactoryManager.h:36, BSTDerivedCreator.h:21: `Create` is the virtual `CreateImpl`, 52803 in the engine), then the fill and `queue->AddMessage(strings->topMenu, kInventoryUpdate, data)` the fork already has. CommonLib surface only; the object has the engine's vtable and heap, so `ProcessCommands` deletes it correctly. Recommended; keep `Shows()` as the filter and post from the game thread after the change lands, as the earlier read said.
- C. Hand construction: `RE::malloc<RE::InventoryUpdateData>()` (MemoryManager.h:113), write the vtable from `REL::Relocation<std::uintptr_t>{ RE::VTABLE_InventoryUpdateData[0] }.address()` (the header has no `VTABLE` member for `stl::emplace_vtable`, PCH.h:507), `unk08 = 0`, the two fields. Replicates 52803 by hand; a CRT `new` or CommonLib's compiled vtable would be freed through `MemoryManager::Deallocate` (68117) by the deleting destructor 52836 and corrupt the heap. Not worth it while B exists.
- Never 82169 for this name. Side finding: 1.6.1170's `InterfaceStrings` has "Login Menu" at +0x1A0 before "Marketplace Menu", so every member CommonLib places from +0x1A0 on is off by eight; `inventoryUpdateData` and `topMenu` are below it and unaffected (HYPOTHESIS).
